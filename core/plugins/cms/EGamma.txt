Scale and smearing corrections for UL: UPDATED

    Updated 14th Oct 2024: Unfortunately, it was found that Run2 UL NanoAODv9 had been produced with outdated energy correction files described below (see notes on 14th Sept 2021). The detailed impacts of outdated correction files can be seen in the presentation [link]. The effect on electrons is marginal. However, there can be non-negligible loss of photons due to the different R9 values between electrons and photons. The issue can be treated by 1) vetoing the affected region in the era 2016preVFP (1.5 < |η| < 2 & R9 > 0.98), or 2) reprocessing NanoAOD privately (recipes to be announced). Note that this issue will be fixed from NanoAODv15 and onwards. 

    Updated 17th February 2023, https://cms-talk.web.cern.ch/t/ul2016-miniaod-issue-with-s-s-solvable-on-the-fly-by-using-egamma-postreco-tool/20461 Make sure to use egamma postreco tool as described below, specially for 2016UL. See the cmsTalk post for more details. 

    Updated on 9th Nov, 2021: The uncertainties provided for UL are the quadrature sum of all the sources (for re-reco we provided the values of each source separately). Please use energyScaleUp/energyScaleDown for the shifts. These are the only two variables which should be used for uncertainties on energy scale in UL 

    Updated on 14th Sept, 2021: It was notified by the S+S experts that in the UL2016 files, for electrons with |Eta| between 1.5 to 2 and R9 > 0.98 the scale correction was set as 0. So effectively particles satisfying this criteria would be removed in data (but not MC). This is a very small fraction of the overall stats, and doesn't affect the agreement at the Z peak. In addition, an issue was found in the post VFP file where the scales for the R9>0.96 for |Eta| between 1.0 to 1.44 was set to 1 [Not excluding any events but not applying the derived scale]. With this update, this bug is taken care of. Nothing changes in the instructions at the user level. Please keep following the same as given below. However, make sure that if you checked out things before 14th Sept for UL2016, please redo the commands so that you get the most updated files. 

    * Updated on 12th July, 2021: We missed "runEnergyCorrections=True" in setupEgammaPostRecoSeq, so added it to True. However, this is by default set to True, so should not affect anything but just to be sure. 

    Updated on 7th April, 2021: Recipe to apply scaling systematics to the MC 

    HELP For reference about how to access variables pre and post scale and smearing corrections, read this: https://twiki.cern.ch/twiki/bin/viewauth/CMS/EgammaMiniAODV2#Applying_the_Energy_Scale_and_sm 

    ALERT! WARNING

    Normally we recommend to apply both scale and smearing systematics to the MC, as mentioned here: https://twiki.cern.ch/twiki/bin/viewauth/CMS/EgammaMiniAODV2#Applying_the_Energy_Scale_and_sm. However, in the UL samples (both Summer20MiniAOD and Summer20MiniAODv2) the scale systematics for the MC were not included (due to the txt files). This problem can be solved in 2 ways:

        By applying the scale systematics to data and the smearing systematics to MC.

        By following the recipe below ("Recipe for running scales and smearings using EgammaPostRecoTools ") to be able to compute the scale systematics in MC and apply both scale and smearing systematics to the MC (recommended solution).

For pre-UL samples, we recommend to apply both scale and smearing systematics to the MC (without the need of running EgammaPostRecoTools).

Recipe for running scales and smearings using EgammaPostRecoTools

    RECIPE for CMSSW_10_6_X where X >= 19 (scaling systematics applied to MC as done with pre UL and this is what we recommend)

          setenv SCRAM_ARCH slc7_amd64_gcc700  #### for bash shell: export SCRAM_ARCH=slc7_amd64_gcc820
          cmsrel CMSSW_10_6_19
          cd CMSSW_10_6_19/src
          cmsenv
          git cms-init  

          git cms-addpkg RecoEgamma/EgammaTools  ### essentially just checkout the package from CMSSW
          git clone https://github.com/cms-egamma/EgammaPostRecoTools.git
          mv EgammaPostRecoTools/python/EgammaPostRecoTools.py RecoEgamma/EgammaTools/python/.
          git clone -b ULSSfiles_correctScaleSysMC https://github.com/jainshilpi/EgammaAnalysis-ElectronTools.git EgammaAnalysis/ElectronTools/data/
          git cms-addpkg EgammaAnalysis/ElectronTools

          scram b -j 8
         

    RECIPE for CMSSW_10_6_X where X >= 19 (scaling systematics still applied to data - this is what has gone in Summer20MiniAODv2 samples and hence the recipe still stays here. We will remove this recipe soon since the above one is the one which is recommended)

          setenv SCRAM_ARCH slc7_amd64_gcc700  #### for bash shell: export SCRAM_ARCH=slc7_amd64_gcc820
          cmsrel CMSSW_10_6_19
          cd CMSSW_10_6_19/src
          cmsenv
          git cms-init  

          git cms-addpkg RecoEgamma/EgammaTools  ### essentially just checkout the package from CMSSW
          git clone https://github.com/cms-egamma/EgammaPostRecoTools.git
          mv EgammaPostRecoTools/python/EgammaPostRecoTools.py RecoEgamma/EgammaTools/python/.
          git clone https://github.com/cms-data/EgammaAnalysis-ElectronTools.git EgammaAnalysis/ElectronTools/data/
          git cms-addpkg EgammaAnalysis/ElectronTools

          scram b -j 8
         

    RECIPE for CMSSW_10_6_X where X < 19 (scaling systematics still applied to data)

          setenv SCRAM_ARCH slc7_amd64_gcc700  #### for bash shell: export SCRAM_ARCH=slc7_amd64_gcc820
          cmsrel CMSSW_10_6_2
          cd CMSSW_10_6_2/src
          cmsenv
          git cms-init  
          
          #### *The step below depends on the CMSSW version. So please read carefully* 
          git cms-merge-topic jainshilpi:ULV1_backport106X_forUsers  ### if CMSSW < 10_6_16
          ##### for working in CMSSW_10_6_16 and beyond, please use this: git cms-merge-topic jainshilpi:ULV1_backport10616_forUsers

          git clone https://github.com/cms-egamma/EgammaPostRecoTools.git
          mv EgammaPostRecoTools/python/EgammaPostRecoTools.py RecoEgamma/EgammaTools/python/.
          git clone https://github.com/cms-data/EgammaAnalysis-ElectronTools.git EgammaAnalysis/ElectronTools/data/
          git cms-addpkg EgammaAnalysis/ElectronTools

          scram b -j 8

HLT Zvtx Scale Factor

    there is an allowed Z region for an electron to be in the HLT which is obtained by the online beamspot. There were problems in the begining of 2017, which means that the z region was too small and efficiency suffered. This can not be determined with Z->ee tag & probe as the tag & probe have the same zvtx. Care must be taken with e-mu tag and probe as this will include it as the muon triggers were not as effected
        for more details, please see this talk from the 07/02/18 EGM Meeting 
    the MC efficiency is one so the efficiency of the online Z region cut in the HLT and the scale factor for MC are identical
    events selected using electron triggers which use pixel matching require an additional scale factor. As it is event level, it should be applied only once per event, no matter how many electrons were required to be triggered
    this only needs to be applied in 2017, 2016 & 2018 are fine
    these numbers are considered final by E/gamma (and are unchanged), and still needed in UL2017 because the issue was in trigger which is not possible to fix by re-reco.
        the 2018 number measured to be > 0.99976 and is taken to be 1.0 as a 0.02% inefficiency dwarfed by other efficiency systematics

New Procedure for Non-Standard ID Usage in CMS

Starting from 2017 we would like to introduce an official policy for electron/photon ID usage in CMS with a clear timeline and recommendations for analyses to be approved by E/gamma.

The EGamma POG strongly recommends to use standard electron and photon ID working points and tools. Those are developed and optimized by e/gamma experts. Details on their implementation are provided together with corresponding approved scale factors. The official e/gamma ID are all implemented in the VID format in CMSSW, and this is the tool we recommend to use rather than re-implement the IDs by hand in your analyses.

If an analysis needs an ID which is not an e/gamma maintained ID, we ask the analyzers to present the performance of their own ID together with a physics motivation at one of our e/gamma ID meeting. All the non-standard IDs must be approved well in advance by e/gamma (about a month) and we now require for all non-standard IDs, to produce a VID implementation. We are preparing a detailed tutorial about the VID implementation and usage in CMS. The documentation in the twiki will be updated shortly.

Data/MC scale factors should be provided to e/gamma in the same format as centrally provided ones so we can transmit the results to other users. The tag and probe tool is available and well documented in the corresponding twiki.

In order to have a clear overview of the status of analyses in CMS not using standard IDs, we will ask soon to PAG contacts to provide a list of all E/gamma using analyses, together with trigger, ID, energy regression version, CMSSW version information, typical energy range of analysis (including signal). A google spreadsheet will be circulated soon.

If you are using standard photon ID for high pT region (>200 GeV ), some detailed studies of efficiency and SF is needed. Please consult this twiki for our recommendation:

https://twiki.cern.ch/twiki/bin/view/CMS/EGMPhotonIDHighPtPhotons

Please contact EGM POG if you need more details on this.

Instructions for applying electron and photon ID

Please make sure that you read this twiki: https://twiki.cern.ch/twiki/bin/view/CMS/EgammaPostRecoRecipes

Users no longer need to configure the E/gamma IDs (VID) by hand, post reco tool will do it all for you.

The latest RunII electron ID names are:

cutBasedElectronID-Fall17-94X-V2-veto, cutBasedElectronID-Fall17-94X-V2-loose, cutBasedElectronID-Fall17-94X-V2-medium, cutBasedElectronID-Fall17-94X-V2-tight, mvaEleID-Fall17-iso-V2-wp90, mvaEleID-Fall17-iso-V2-wp80, mvaEleID-Fall17-noIso-V2-wp90, mvaEleID-Fall17-noIso-V2-wp80. There are two other electron MVA IDs, which is not supported by EGM anymore, which means that EGM will not provide scale factor for them, and if you use them you need to produce scale factor yourself and give a presentation in EGM POG for the approval of the scale factor. These two unsupported IDs are: mvaEleID-Fall17-noIso-V2-wpLoose, mvaEleID-Fall17-iso-V2-wpHZZ .

for(const auto& pho : iEvent.get(phoToken_) ) {

similarly,

for(const auto& ele : iEvent.get(eleToken_) ) {

bool isPassMVAiso90 = ele.electronID("mvaEleID-Fall17-iso-V2-wp90");

}

VID Usage Tutorial (old, some parts superseeded by egamma post reco tools)

The VID (versioned identification) framework is the framework used by E/Gamma POG to implement the different selections for Electrons and Photons. All standard IDs are implemented in this way. It is highly recommended that users who have a custom set of ID requirements use the VID implementation. The framework produces an unsigned int which is a bitmap of which cuts passed and failed for a given ID. In the easiest implementation in the ntuplizer only a single bit is saved saying if the electron/photon passed the required ID. The tutorial (watch out, it's old) is available here

Correctionlib JSONs:

The 2022, 2023, and 2024 Scale and Smearing corrections are provided separately for electrons and photons. In addition, two "flavours" can be used for 2022 and 2023: a standard one, and an eT-dependent one (marked as such in the json file name). The eT-dependent corrections generally yield a better data/MC agreement for objects in the phase space they were derived upon. For 2024, only eT-dependent corrections are available. The Scale and Smearing corrections should not be used for electrons and photons below ~15 GeV and should be used with caution between 15 and 20 GeV, as they were not tuned for this pT range. They might also be ineffective at very high pT (hundreds of GeV).

We recommend to use the eT-dependent corrections and to get in contact with the EGM POG should you observe unexpected/unwanted behaviours. For an explanation of the two different methods used to derive the standard and et-dependent corrections, please follow the links.

Please note that the correct eta to use to fetch the electron and photon S&S corrections is the supercluster eta (that is Electron(Photon)_superclusterEta in NanoAOD v15). For NanoAOD versions < 15 this variable is not directly available, but one can calculate it as "Electron_eta + Electron_deltaEtaSC". This is unfortunately not the case for photons, for which deltaEtaSC does not exist. In this latter case, Photon_eta can be used instead. Ultimately, the difference between using supercluster era or eta should be minimal.

Scale and Smearing Example

CHECKOUT THE LATEST APPLICATION EXAMPLE:

https://gitlab.cern.ch/cms-analysis-corrections/EGM/examples/-/blob/latest/egmScaleAndSmearingExample.py

The purpose of scale and smearing (more formal: energy scale and resolution corrections) is to correct and calibrate electron and photon energies in data and MC. This step is performed after the MC-based semi-parametric EGamma energy regression, which is applied to both MC and data (aiming to correct for inherent imperfections that are not in principle related to data/MC differences like crystal-by-crystal differences, intermodule gaps, ...). The scale and smearing values are extracted from matching the Zee peaks in data and MC. Usually, energies in data are shifted to the right since, on average, the measured energy is underestimated compared to MC. The energies in MC are smeared out stochastically since the predicted resolution in MC is optimistic. More information on the methodology can be found in https://indico.cern.ch/event/1259025/#49-introduction-to-residual-sc.

You have to consider the following points when applying scale and smearing:

    Energies in data are scaled. Do not apply scale corrections to MC in your analysis.
    Energies in MC are smeared. Do not apply the smearing to data in your analysis.
    To consider uncertainties in the statistical analysis, apply them to MC on top of corrected (smeared, but not scaled) nominal quantities. 

In Run 3, separate JSONs exist for electrons and photons again (was also present in early Run 2, but not in UL Run 2). Make sure you pick the right one for the object that you are considering.

Electron ID Working Points (WP) definition

Four standard working points are provided

    Veto (average efficiency ~95%)
        Use this working point for third lepton veto or counting 
    Loose (average efficiency ~90%)
        Use this working point when backgrounds are rather low 
    Medium (average efficiency ~80%)
        This is a good starting point for generic measurements involving W or Z 
    Tight (average efficiency ~70%)
        Use this working point for measurements where backgrounds are a serious problem 

Note that for measurements focusing on high energy (~1+ TeV) electrons, a dedicated HEEP ID is provided see a dedicated link on the EgammaIDRecipesRun2 twiki. HEEP ID for Run3 has not been developed yet, till then Run2 HEEP ID mentioned above can be used and expected to provide reasonable performance. In case you find worse performance using the Run2 HEEP ID till we mention a dedicated HEEP ID for Run3 please report to us.

Many times it is useful to add or remove individual cuts of a selection. This could be for side band studies, removing isolation cuts or for studying the efficiency of a single cut or an "N-1" efficiency/distribution where "N-1" means "apply all N selections except the 1 under study".

MVA Based Electron ID for Run 3

This twiki describes different aspects of the usage and development of the MVA based identification criteria for Run 3. It included several recommendations by EGM POG including the official scale factors. It also documents the guidelines and useful tools for development of custom ID criteria and for the derivation of the scale factors. Please contact EGM POG if you need more details.

Electron MVA ID Working Points (WP) definition

There are two different types of id developed for Run 3 - isolated and non-isolated. For both IDs, two working points, wp80 and wp90, are defined. These correspond to the 80% and 90% efficiency using the training datasets.

Running EgammaPostRecoTools to include correct noIso IDs

There is a bug in the Run3 noIso MVA electron IDs, in that the barrel IDs implement isolation (they are in fact exactly the Iso ones). This affects the IDs embedded in slimmedElectrons in Run3 MiniAOD (v3, v4). If you are working on MiniAOD and need to use these noIso IDs, you can run the EgammaPostRecoTools, that will take your slimmedElectrons collection and create a new collection with the same name and the correct IDs on top. The procedure is quite simple and is detailed below.

You will need to use a CMSSW release >=13_3_0, as the fix is there starting from that release.

cmsrel CMSSW_13_3_0
cd CMSSW_13_3_0/src
cmsenv
git cms-init
#now add in E/gamma Post reco tools and compile
git clone git@github.com:cms-egamma/EgammaPostRecoTools.git EgammaUser/EgammaPostRecoTools
scram b -j 8

Then, in your Analyzer's cmsRun config file:

from EgammaUser.EgammaPostRecoTools.EgammaPostRecoTools import setupEgammaPostRecoSeq
setupEgammaPostRecoSeq(process,
                       runEnergyCorrections=False, #Only set it to True if you want to pick the latest Scale&Smearing corrections.
                       runVID=True,
                       era='2022-Prompt',
                       eleIDModules=[ 'RecoEgamma.ElectronIdentification.Identification.mvaElectronID_RunIIIWinter22_iso_V1_cff',
                                      'RecoEgamma.ElectronIdentification.Identification.mvaElectronID_RunIIIWinter22_noIso_V1_cff',
                                      'RecoEgamma.ElectronIdentification.Identification.cutBasedElectronID_Winter22_122X_V1_cff']
                      )

This will create a sequence "process.egammaPostRecoSeq" that you have to add to your Path:

process.p = cms.Path ( process.egammaPostRecoSeq * process.MyAnalyzer)

The Photon_vidNestedWPBitmap branch in NanoAOD samples keeps this information ( LINK). In order to access the bit map decision for different ID cuts (0:fail, 1:loose, 2:medium, 3:tight), one can use the following piece of code.

 std::vector<bool> parsePhotonVIDCuts(int bitMap, int cutLevel){
// * | Int_t VID compressed bitmap ( [[MinPtCut][MinPtCut]],PhoSCEtaMultiRangeCut,PhoFull5x5SigmaIEtaIEtaCut,PhoHcalOverEcalWithEACut,ChgHadIsoWithEAQuadScalingCut,ECalClusIsoWithEAQuadScalingCut,HCalClusIsoWithEAQuadScalingCut), 2 bits per cut*
   bool passSIEIE = (bitMap>>4&3) >= cutLevel;
   bool passHoverE = (bitMap>>6&3) >= cutLevel;
   bool passChIso = (bitMap>>8&3) >= cutLevel;
   bool passEcalIso = (bitMap>>10&3) >= cutLevel;
   bool passHcalIso = (bitMap>>12&3) >= cutLevel;
   bool passID = passHoverE && passSIEIE && passChIso && passEcalIso && passHcalIso;
   std::vector<bool> cuts;
   cuts.push_back(passID);
   cuts.push_back(passSIEIE);
   cuts.push_back(passHoverE);
   cuts.push_back(passChIso);
   cuts.push_back(passEcalIso);
   cuts.push_back(passHcalIso);
   return cuts;
}
}

Run3 MVA Photon:

Introduction

This page discusses EGM recommendations for a general purpose multivariate photon identification methods or Run 3. In the MVA approach, one forms a single discriminator variable that is computed based on multiple parameters of the photon object and provides the best separation between the signal and backgrounds. One can then cut on discriminator value or use the distribution of the values for a shape based statistical analysis.

New general purpose photon MVA tunings are normally derived by EGM for each new dataset of real data or new MC production.

While the MVA discriminators provided by EGM are expected to be used in bulk of CMS analyses, the MVA cut values are usually analysis specific. EGM provides one or two baseline working points, but it is expected that individual analyses will optimize the cut values as they find necessary for the optimal analysis sensitivity.

*Important notice*: If you are using generic photon ID for high pT region (>200 GeV ), some detailed studies of efficiency and SF is needed. Please consult this twiki for our recommendation: EGMPhotonIDHighPtPhotonsRun3 . Please contact EGM POG if you need more details on this.

Event Selection

The events are selected based on the following criteria. The signal events are then reweighted to match the background in the phase space.

    Double EM Enriched γ+jets MC samples used both for signal and background
    Photon Pt > 10 GeV
    Ecal acceptance cut : |η| < 2.5 and NOT in barrel–endcap overlap (1.4442 < |η| < 1.566)
    Signal : prompt photons matched to gen matching criteria
    Background : fake photons 

    Gen matching criteria:
        PDG ID == 22
        IsPromptFinalState () and fromHardProcessFinalState()
        dR(recoPhoton, genPhoton) < 0.10
        Relative pT difference between reco and gen photon (dpT/pT < 0.20)
